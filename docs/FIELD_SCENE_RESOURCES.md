# 多场景资源选择（开发中）

市政厅需要第二套 Field Room／Map、NPC 和音乐。原资源目录的这些类型绑定为单例，直接覆盖全局加载器还会使旧场景持有的 view 失效。因此先增加受检引用，再实现平台资源生命周期与实际场景内容；目前尚未增加市政厅可游玩范围。

目录容器格式仍为 1，能力 9 才允许 FieldRoom／FieldMap／FieldStory／FieldMusic／FieldAudio／FieldMusicZones 的额外绑定（独立 ID 从 1024 起）；原单例 ID 必须保留。其他类型与旧能力的限制不变。`path(role,id)` 按类型和身份查询，错误类型不能得到路径。旧资源目录目前仍生成能力 8、47 项，输出字节保持不变。

World Links 格式仍为 1，新增能力 2 的 SceneAssets（36 字节）和 NpcBindings（4 字节）两个节。每个 Field Scene 恰有一条资产记录；NPC 引用必须有唯一的范围归属、无重复或遗留项；音乐三项齐全或全空。绑定目录时验证每个资源类型，并拒绝目录中无人拥有的场景资源。能力 2 可表达同场景门移动；能力 1 保留原来的拒绝规则和单场景目录解释，遇到多个字段资源集必须拒绝歧义。

测试旧夹具直接取自已构建提交 cbdd992 的目录与 World Links，没有改写其字节。新增第三场景仅为编解码夹具，不是原版地图。GCC9 ASan/UBSan 的新元数据 66 项检查、已有目录 5,426 项和桥头剧情回归通过；三个 Python 测试覆盖版本、身份、类型、缺失默认项、截断与能力不匹配。日志在 reports/field-scene-resources。此阶段未更改规则或游戏存档格式；交叉构建与模拟器结论另行记录。

待完成：来源 Scene 编译与路由；平台按场景选择及原子资源所有权；原版市政厅图层、碰撞、内部门、音乐和初始 NPC 对话；实际输入路线及负向加载恢复。不能在旧 FieldScene 仍活跃时覆写其 Room／Map 数据。

资源生命周期基础：新增不可重新加载的 FieldSceneResources，按类型／身份读入并验证目录长度与 CRC，拥有 Room／Map／Story／Mick／NPC 和区域音乐元数据；核对场景 ID／来源、共享旗标域、NPC 子类型和音乐／音频绑定。原目录与 Links 销毁后，已加载元数据仍保持独立有效。失败不发布半成品；已有场景的 view 不被下一次 load 覆写。新增 32 项 GCC ASan/UBSan 检查通过，平台接入仍在开发。

平台现在按门的目的场景选择并先加载独立元数据，再准备借用 view 的 FieldScene；候选 bind 的旗标主机优先指向候选场景，只有提交时才替换旧所有者，所有退出路径按 Scene→Resources 顺序销毁。Mick／NPC 与剧情音效也从候选所有者读取。当前跨 Field 场景和不同音乐集的切换仍显式拒绝，待接入跨场景音频生命周期；尚未生成市政厅可玩资源。
