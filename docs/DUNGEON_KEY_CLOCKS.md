# 墓穴钥匙与锁门时钟

本分支依赖 #71。独立 ENCKLC01 format1／capability1 资源保存固定上游的七个动画、三种属性拥有者、两个原版音源身份，以及原有 ENCDKEY1 六个钥匙／锁门身份。3812 字节候选由受检来源生成；没有新增正式 RomFS、目录角色、规则身份或存档编码，也没有开放墓穴地图。

`DungeonKeyClockPlayer` 执行受检的帧、可见性、Vector2 连续曲线、音频属性和固定父节点绑定。钥匙 `Use Key` 的位置曲线保留原版 `0.366021` easing；没有用离散位置或固定动画时间替代。该动画是原资源中声明的可请求时钟，正常拾取方法没有调用它，本实现也不会为拾取自行播放它。

`DungeonKeyClocks` 把这些时钟接到原有钥匙／锁门方法状态。按原节点顺序先推进锁头、再推进门本体；门动画的 `open` 和锁头 `play_anim` 请求等待明确的空闲帧边界。拾取音频占用、隐藏、延迟禁用碰撞、音频完成删除、已保存的门与钥匙、计数和旗标通知保留各自顺序。输出包括原方法的同步观察快照和按原节点归属的声音请求；正式世界与媒体拥有者必须先接受整个候选批次再发布状态。

场景 epoch、完整旗标覆盖、拥有者类别、旧回调、删除后调用、未知动画角色、事件／延迟队列容量及非法时间均明确拒绝。单次推进、回调、空闲帧或退役失败保留之前的状态和请求；退役清除待执行调用，并请求停止仍占用的本地声音。资源以不可变共享拥有者保持，重新加载不会使旧时钟或方法视图悬空。

原版有两个具体的信号问题，不能自行补成正常完成事件：

- 门本体和锁头场景都把 `animation_finished` 连到不存在的 `_on_AnimationPlayer_animation_finished`。
- 锁头的原 `CutsceneObject._ready` 另将动画名与绑定参数传入 `emit_signal`，实际尝试发出 `Open`／`RESET`，没有发出 `animation_ended`。

共享核心分别输出这些已审查的诊断，保持原版后续存活状态；未知诊断、方法或绑定仍拒绝。测试退出码 17 是包含这些原版错误的独立对照程序结果，不能解释为完整游戏正常退出或无错误运行。

验证与证据：

- 两次官方 Godot 3.6.2 运行，各 461 个观察结果完全相同，覆盖七个原生动画、连续曲线中间点、边界、门本体／锁头并行、长时间跨越、正常拾取与音频完成、已保存对象。每次实际记录并逐项核对 13 个原版诊断。
- 另以原生 IDLE 调度确认：动画停止后的六个空闲帧没有额外属性写入。早期探针在停止后仍强制调用公开 `advance`，产生额外音频属性写入；原始观察和共享核心不匹配记录保留。修正的是探针调度，没有改原脚本、资源或冻结期望。
- 22,131 项直接 GCC 9.4 ASan+UBSan 检查通过，保留正常泄漏检查，包括整段原版观察、失败回滚、不可变拥有者、容量、音频浮点下界及数据损坏拒绝。编译／执行的输入指纹前后不变，实际进程退出码 0。此结果不是本地 `make test`、Clang 或交叉构建通过。
- 8 项 Python 来源、编解码、重复原版运行与负向检查通过。Windows 配置／发现得到 305 项 CTest、1383 项 Python（1000 汇总＋383 专用）；这是元数据，不是 Windows 测试通过。Visual Studio 配置需要实际 `-C Debug`，收集适配器仅补该参数。

原始记录见 `reports/dungeon-key-clocks`。首次探针漏带原项目的 `unused_signal=false` 设置而导入失败，修正时只采用已核对的原项目设置；其他未知错误继续阻断。本地前两次编译调用分别误列不存在的 CRC 源文件、漏列文件读取实现，另一次证明收集器在启动前出现语法错误，均保留相应失败层次。
