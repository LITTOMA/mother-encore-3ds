# 开局场景数据转换

基线是 `upstream.lock` 中的 Act 2 v0.4.1.0。这里记录的是原生场景数据转换，
还不是可玩地图适配。3DS 当前仍只显示底图，人物、家具绘制、碰撞响应及开局剧情没有接入。

## 可重复执行

使用已校验的官方 Godot 3.6.2，引擎程序和中间项目均放在 build/。
每次使用新的工作目录与报告目录，避免拿旧缓存或旧输出当作成功结果：

```powershell
python tools/run_scene_reference.py `
  --godot build/m1/godot/bin/Godot_v3.6.2-stable_win64.exe `
  --work build/m2/scene-reference-next `
  --reports reports/m2-scene-reference-next
```

`--micro-only` 只运行小型语义样本。完整入口先验证小型样本，再准备房屋静态依赖、
等待编辑器完成导入，最后输出数据。单个引擎进程有55秒期限，失败和超时输出直接留在报告文件。
正常导入/导出日志中出现 ERROR 或 WARNING 就拒绝生成成功收据；不以退出码0单独判断成功。
负例必须非零退出、包含指定拒绝原因，并且不产生部分输出。
资源导入由工作副本内的开发插件等待扫描完成后退出，避免 `--editor --quit` 中途终止扫描。
传给 Godot 的自定义路径使用 `--encore-scene=...` 单一参数；分开的 `res://...` 参数可能被 Godot 当作要启动的主场景。

## 数据范围与边界

`scene_reference.py` 验证真实 HEAD、只读源码状态、清单版本和每个依赖的原始 SHA。
房屋静态闭包目前有71个文件。仅复制需要的文本资源、图像、声音、字体和 Shader 到 build/ 工作副本，
没有将这里的字体或声音打入 RomFS/发布包，也没有使用本机字体。
DynamicFontData 的 `font_path` 是额外的原生加载依赖，单独记录，不能只扫描 ext_resource。

脚本引用及信号声明在工作副本内隔离。外部脚本的原始文件仍有指纹，嵌入脚本保留完整声明及指纹；
每个挂载和连接都有源码文件、行号及原始声明。未知语言、脚本被用于其他字段、
未挂载脚本、未知文本资源版本、重复资源ID、危险路径和不认识的路径转义均阻断。
这些隔离项是未实现机制，不是忽略规则；全量兼容绑定表没有新增批准。

`scene_data.gd` 使用 Godot 原生 PackedScene 实例化数据，且不将实例加入场景树。
生产副本没有游戏脚本挂载，因此不会运行游戏脚本的 `_init`、`_ready` 或逐帧逻辑。
孤立测试样本保留简单脚本，以检查脚本默认值；其 `_ready` 一旦运行就断言失败。
生产数据中的原版脚本默认值仍未获得机制适配，不能用原生节点默认值冒充它们。

输出包含：

- 展开的实例/继承节点、原生默认值、实例覆盖及 Node2D 世界变换；
- 原始 SceneState 的覆盖字段与实例引用，保留脚本自定义字段，供后续适配器使用；
- TileMap 原生解码后的坐标、tile ID、autotile 坐标、翻转、转置和原点；
- TileSet、动画、材质与碰撞资源图，以及实际碰撞 shape owner 和 Godot 的多边形分解结果；
- 所有整数使用显式 int64 十进制字符串，避免 JSON 数字损坏64位值；
- 图像/音频/字体只记录引用及尺寸，不把二进制伪装成已适配内容。

资源图中的数字ID只是本次导出的局部引用，不能作为存档身份。
实际 MapDef/ObjectDef 的持久身份登记及对应的 C++ 内容包仍待实现。
未知 Variant、非有限数字、悬空资源、丢失父节点及未实现的 InstancePlaceholder 都明确拒绝。
数据的 `native_compatible` 必须为 false，`require_gameplay` 始终阻断；
脚本默认值、动态工厂、信号、方法轨道及实际游戏行为没有获得这次数据转换的批准。

## 发现并修正的坐标问题

样本中基础场景的 CollisionShape2D 在 `(1,-2)`，派生场景覆盖为 `(2,-1)`。
Godot 在进入场景树前的 `shape_owner_get_transform` 仍可能返回基础坐标，
尽管节点本身和全局变换已经采用覆盖值。直接使用该缓存会导出错误碰撞位置。

现在同时记录 `cached_transform_before_enter_tree` 和已展开子节点的 `transform`，
几何适配使用后者。小型样本分别验证两个结果，不把失败的期望修改成“通过”。
该差异是实例尚未进入树时的缓存生命周期；不代表已经验证了原版运行时碰撞响应。

## 当前真实证据

最新场景结果在 `reports/m2-scene-reference-reviewed/`：497节点、381资源、21个 SceneState；
Below/Objects/Above 分别有1/14/276个格子。资源数包括 shape owner 产生的原生凸多边形。
隔离项是25个脚本挂载与29条信号声明。receipt.json 保留引擎、工具、来源记录及数据文件指纹。
小型样本核对默认值、继承覆盖顺序、实例独立性、世界/碰撞坐标、64位值和信号声明；
3D Variant 及延迟实例负例被拒绝且没有部分输出。
早期坐标不匹配的导出不属于通过结果。

这是 Windows 官方引擎的场景数据参考。完整原版游戏参考、3DS设备显示与玩法仍需分别验证。
该历史阶段的桌面测试和 ASan/UBSan 各为 4/4 组通过，
真实3DSX/CIA构建与SD测试ZIP生成成功。没有因为导出成功改变现有3DS查看器的功能声明。
下一步从这些已展开的数据生成游戏专用 MapDef/SpriteDef/碰撞定义，
对照原版 Player 与 controlsManager 接入移动，然后实现开局房屋的事件和剧情。

后续人物动画适配发现，Godot `JSON.print` 会把本次资源中的浮点值缩短为六位小数，
例如关键帧时间 `0.0833333` 输出为 `0.083333`。整数仍按 int64 字符串保真；
当前通用场景 JSON 的浮点数不能作为精确动画时序或精确物理的最终依据。
人物动画适配器另从原生 Animation 读取17位小数文本，核对缩短值后编译原生 float 精度。
通用浮点编码的升级仍待后续场景/物理接入处理，不能声称现有导出器已无损保留所有数字。
